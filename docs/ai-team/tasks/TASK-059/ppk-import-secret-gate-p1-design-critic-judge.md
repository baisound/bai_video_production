# TASK-059 P1 — PPK Secret Gate Design / Critic / Judge

Date: `2026-08-26`

Status: `DESIGN_BOUND_P1A_IMPLEMENTED_LOCAL_P1B_NEXT`

Development depth: `DEV-4 PRIVACY, AUTHORIZATION AND RELEASE INTEGRITY`

## Decision and authority boundary

P1 will be a short-lived Windows-only helper that authenticates one encrypted
PuTTY PPK Version 3 Ed25519 key and, only after an exact in-session Owner
confirmation, invokes the existing TASK-029 R9B one-shot custody provision
boundary.

This document authorizes design only. It does not authorize implementation,
real PPK selection, passphrase entry, decryption, DPAPI custody, signing,
Knowledge Pack mutation, Release, Deploy or Production.

TASK-059 P0 remains body-free preflight owner. TASK-029 R9B remains the only
raw 32-byte Ed25519 seed validation and Windows Current User DPAPI custody
owner. R9C remains local signing owner and R9A remains verification owner. P1
must not add another store, signer, key agent, promotion path or entrypoint.

## Required process topology

```text
Operator UI
  -> exact P0 record, PPK bytes and masked passphrase through inherited pipe
  -> short-lived Windows P1 helper
       1. reparse and bind exact P0/file/public/fingerprint coordinates
       2. derive 80 Argon2id bytes
       3. decrypt AES-256-CBC ciphertext
       4. verify HMAC-SHA-256 over the exact PPK v3 MAC preimage
       5. parse canonical Ed25519 private exponent
       6. derive and cross-check public key
       7. emit body-free READY challenge
  <- direct Owner Import or Cancel confirmation bound to that challenge
  -> helper calls existing R9B confirm/provision/read-back exactly once
  <- body-free TASK-059 bridge receipt and canonical R9B receipt
  -> helper clears mutable buffers where possible and terminates
```

No secret may be placed in argv, environment variables, command text, temp
files, clipboard, logs, exception text, telemetry, Evidence, Git, PR or CI.
Spawn without a shell, inherit only explicit anonymous pipe handles and reject
console/stdin fallback.

## Phase A — capability and immutable input admission

Before passphrase receipt, both parent and helper verify:

- Windows native runtime and Current User DPAPI availability;
- `cryptography>=46,<51` with Argon2id, AES-CBC, HMAC-SHA-256 and Ed25519;
- exact P0 admission and `preflight_sha256`;
- current PPK/public-file hashes and Owner-confirmed OpenSSH fingerprint;
- destination custody identity, Owner scope and path coordinate;
- destination absence and non-symlink/non-directory state; and
- no existing R9B custody overwrite, replacement or rotation.

Any drift terminates before secret input. P1 must not install, download or
silently choose an alternate cryptographic backend.

## Phase B — secret input

The UI uses a masked passphrase control with clear Cancel. Paste is disabled by
default but may be explicitly enabled for one attempt. No reveal, history,
autocomplete, accessibility-value logging or crash capture is permitted.

The parent encodes the entered Unicode value once as strict UTF-8 into a bounded
mutable buffer. The helper accepts one frame of `1..1024` bytes and rejects
NUL. Parent clears the control and transport buffer after delivery. Python
cannot guarantee erasure of every interpreter/library copy, so helper process
termination is the authoritative memory reclamation boundary.

A synthetic non-ASCII passphrase key generated by the pinned PuTTYgen version
must pass before a real-key Gate. Until then, native admission fails closed
instead of guessing legacy encoding.

## Phase C — PPK v3 authentication

The helper independently reparses the PPK; P0 parsed fields are coordinates,
not secret-operation input. Only PPK v3, `ssh-ed25519`, `aes256-cbc` and
`Argon2id` are admissible.

Argon2id derives exactly 80 bytes using the PPK salt/bounded parameters and
empty Argon2 secret and associated-data inputs:

- bytes `0..31`: AES-256 key;
- bytes `32..47`: CBC IV;
- bytes `48..79`: HMAC-SHA-256 key.

Decrypt the complete AES-block-aligned private ciphertext without unpadding.
Construct the HMAC input as five SSH binary strings: algorithm, encryption,
exact comment bytes, decoded public blob, and complete decrypted private blob
including random AES padding. Compare the calculated and stored MAC in constant
time.

Wrong passphrase, ciphertext/comment/public tamper, malformed plaintext and MAC
mismatch all expose only `ERR_PPK_SECRET_AUTHENTICATION_FAILED`. No decrypted
parse result is trusted or returned before MAC success.

## Phase D — Ed25519 conversion and cross-check

After MAC success, parse the first SSH `mpint` as the Ed25519 private exponent.
Require canonical positive encoding normalizable to exactly 32 bytes. Remaining
authenticated bytes are PPK padding and are never interpreted or returned.

Derive the raw public key with
`Ed25519PrivateKey.from_private_bytes(seed)` and require equality with the
authenticated PPK public blob, separate RFC4716 public blob, P0 signer-key ID
and exact Owner OpenSSH fingerprint. No seed, public-key body, plaintext, KDF
output, MAC key or passphrase leaves the helper.

## Phase E — exact in-session Human Gate

After authentication, emit a body-free READY challenge containing only random
one-shot session/challenge IDs, P0/file/key/fingerprint coordinates, Owner-scope
and destination-path hashes, custody ID, and expiry no later than five minutes.

The UI displays fingerprint, custody destination and one-shot/no-overwrite
consequence. Import requires a direct click. Enter/Escape defaults to Cancel;
there is no countdown, automatic acceptance, remembered choice or remote
confirmation.

Confirmation reproduces every READY coordinate and nonce. Mismatch, expiry,
duplicate frame, pipe close or parent death cancels and terminates without
custody mutation.

## Phase F — canonical R9B provision

Only after confirmation:

1. call `confirm_owner_signing_key_custody(...)` with exact derived public key;
2. call `OwnerSigningKeyCustodyStore.provision(...)` once with the normalized
   seed and matching confirmation;
3. call `read_receipt()` and require equality.

R9B keeps exclusive locking, symlink rejection, one-shot destination check,
atomic write, DPAPI encryption and key-pair validation. P1 must not prewrite,
delete, rename, replace, repair, roll back or retry the custody file.

If provision may have succeeded but the response was lost, recover through
canonical `read_receipt()`; never repeat import.

## Body-free receipt

A success receipt may contain only identity, P0/file/key/Owner-scope/path
hashes, Human-confirmation hash, canonical R9B custody-receipt hash, timestamps,
and true facts for MAC verification, public rederivation and custody read-back.
Signing, export, Knowledge Pack write/promotion, Release, Deploy, Production
and external-effect authority fields are fixed false.

It must not include a path, comment, salt, KDF output, ciphertext, MAC, public
key body, passphrase, seed, decrypted bytes, DPAPI ciphertext or exception body.

## Failure and recovery

| Boundary | Required outcome |
|---|---|
| P0/file/fingerprint/destination drift | fail before secret input |
| unsupported crypto capability | fail closed; no install/fallback |
| malformed/duplicate/oversized frame | terminate without secret operation |
| Argon2/AES/MAC/private/public mismatch | one generic authentication failure |
| Cancel/timeout/parent death | terminate; no custody mutation |
| destination appears before provision | R9B one-shot state error |
| DPAPI/atomic write failure | preserve R9B error; no automatic retry |
| read-back mismatch | data-integrity failure; stop before signing |
| receipt loss after custody success | read canonical receipt; do not reprovision |

## Required verification

- pinned PuTTYgen v3 Ed25519 synthetic ASCII/non-ASCII fixtures;
- known 80-byte Argon2id, AES and HMAC vectors;
- exact SSH-string MAC preimage including comment and random padding;
- wrong-passphrase/tamper cases collapsed to one public error;
- canonical/noncanonical/short/long/negative Ed25519 mpint cases;
- P0/file/fingerprint TOCTOU and public-crossing negatives;
- frame truncation/duplication/oversize and parent-death cleanup;
- Human Cancel/expiry/mismatch/replay cases;
- fake-cipher tests proving one R9B provision call maximum;
- isolated Windows Current User DPAPI integration;
- no argv/environment/temp/clipboard secret process inspection;
- receipt schema/mirror/admission and secret-substring exclusion;
- TASK-029 R9B/R9C/R9D regression.

Tests use runtime-generated synthetic secrets only. Real Owner key testing is a
separate explicitly approved native Gate.

## Critic

- Critical: Python cannot prove complete in-process zeroization. Resolved by a
  short-lived helper as the authoritative reclamation boundary.
- Critical: parsing before MAC trust permits active-file attacks. Resolved by
  complete documented PPK v3 MAC authentication before private parsing.
- Critical: READY replay could outlive secret context. Resolved by helper-local
  one-shot nonces, exact pipe binding and five-minute maximum expiry.
- High: argv/environment/temp transport leaks. Resolved by anonymous pipes.
- High: PPK replacement after P0 crosses keys. Resolved by helper-side reparse,
  exact P0/file/public/fingerprint binding and public rederivation.
- High: P1 could bypass R9B. Resolved by mandatory existing one-shot
  confirm/provision/read-back APIs.
- High: Unicode ambiguity could authenticate different bytes. Resolved by strict
  UTF-8 and pinned PuTTYgen non-ASCII compatibility Evidence.
- High: response-loss retry could collide with successful custody. Resolved by
  read-back recovery and no automatic retry.
- Medium: distinct errors form an oracle. Resolved by one public authentication
  error after secret receipt.
- Medium: UI capture could retain the value. Resolved by disabled capture,
  history and reveal plus separate Windows UI review.

Residual Critical/High/Medium/Low: `0 / 0 / 0 / 0` for design.

## Judge

Decision: `GO` for this P1 design as the implementation contract.

At this design decision, implementation remained `HUMAN GATE` and required
exact allowed files, pinned runtime compatibility and synthetic-only tests.
The later Owner continuation opened P1A only; real key selection, passphrase,
decryption, DPAPI custody and signing remain separately gated.

## P1A implementation checkpoint

Owner continuation authority admitted a synthetic-only implementation slice.
`owner_signing_key_ppk_secret_auth.py` implements Phases A-D as an internal,
non-exported core. It revalidates exact P0 coordinates, performs Argon2id/AES/
HMAC authentication, normalizes the authenticated Ed25519 mpint, rederives the
public key and exposes the seed only through a helper-local one-shot internal
object. Mutable passphrase, KDF material, plaintext and failure-path seed
buffers are cleared best-effort on every exit.

No filesystem, subprocess, UI, DPAPI, R9B provision, signing or external effect
is present. P1A synthetic tests are `14 PASS`, P0 regression is `26 PASS`, and
P1A plus direct Windows R9A/R9B/R9C regression is `42 PASS`.

P1B next owns only body-free READY/confirmation/receipt contracts and a
fake-cipher/store-tested in-memory R9B orchestrator. Process isolation, UI and
real secret/native execution remain later gates.
